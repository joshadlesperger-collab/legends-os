## First-pass card workflow — seller instruction 2026-11-03

- Prepare correctly, save once, check the batch, then archive verified photos. Verification is a read-only comparison unless a specific persisted mismatch is observed. Never rewrite acceptable titles/descriptions for style or open every full editor by default.
- Generation, preflight and saved readback must share the same factual-description rules. Base cards do not need the literal word "Base" when the title/specifics identify the card. Non-base variants and supported identity facts must remain correct. Preserve accepted text; reject contradictions and unsupported condition/value claims before upload.
- Use one exact selected scope and one bulk workspace where supported. Apply observed shared condition/policy/location corrections once. Reuse valid identity, category and hosted-photo evidence; never repeat a settled identification call merely to clear a review or recover the browser.
- Check every saved card's identity/title, category-specific fields, quantity, condition, description, policies/location and exact upright front/back photo order. A count, thumbnail or sampling is insufficient. Batch readback may replace full-editor traversal only when it retains the same per-card actual values and photo evidence.
- Missing, stale, ambiguous or foreign observations are holds, not permission to edit or upload again. Only actual, scoped mismatches enter the correction plan. Save/reopen the same IDs after corrections; unchanged verified rows need no additional editor save.
- Persist each verified card's receipt and hash-verified photo move without waiting for unrelated exceptions. Leave the batch incomplete until all selected cards finish or have explicit exceptions. Seller-reported publication requires fresh live reconciliation and Listed handling; never recreate those drafts.
- Explicit holder-only optical caveats may be advisory under the standing NM default; keep their text visible and retain the original validated provider result. Unknown warnings, identity uncertainty, ambiguous card damage, visible damage and graded cards remain blocking. Seller condition overrides require retained provenance.
- Test changes against retained inputs/observations before a live batch. Do not debug new workflow code inside a seller batch. Measure complete browser attempts, failures, waiting, corrections and archive time; distinguish proof-validation CPU time from browser/operator work and retain unknown gaps.
- Pricing stays with Grok. Preserve seller prices, shipping, original photos, unfinished inventory, same-ID ownership and the no-publish boundary. These rules do not authorize eBay AI identification, a replacement upload or live listing changes.

## Durable instruction intake and execution

- Before a final response to an execution request, run `node scripts/check-execution-exit.mjs TASK_ID [TASK_ID...]` for the active requested deliverables. A nonzero result means unfinished work: continue available work, or explain the specific external blocker/explicit pause. Missing implementation is work to perform, not an external blocker. Reconcile newly granted permissions before reusing an old blocker. Never represent preparation, task capture, or mocked validation as completion of a live experiment.
- Only say an operation is running after a tool has started it and there is a live session/job identifier. Report completion only from retained evidence. This check is an agent procedure, not a desktop runtime interlock; it cannot force execution after a turn ends. Review recurrence through CAPA rather than claiming a written rule guarantees compliance.

- Before implementing each actionable user request, capture its exact non-secret wording and chat/date provenance in the engineering queue using `node --experimental-strip-types scripts/engineering-work-queue.ts capture PACKET_FILE`. A packet contains `instruction` (id, text, source, capturedAt, taskIds, policyRefs, optional supersedes) and optional new `tasks` using the existing task schema. Link existing tasks instead of duplicating them. Redact credentials; never persist secrets from chat.
- Finite requests require linked tasks with measurable completion criteria; standing constraints require policy references. Mixed requests require both. Questions alone do not create work unless they request an action. Preserve earlier instructions and evidence; capture corrections with explicit supersedes links and reconcile affected tasks without silently erasing work or expanding permissions.
- At each run, read `instructions` and `dispatch`, reconcile new chat instructions with durable coverage, then `claim`, execute and checkpoint. Continue claiming independent eligible work in the same run. A blocked integration is not a reason to abandon unrelated tasks. Do not repeatedly retry unchanged blockers or invent busywork.
- Use a stable run-specific worker name and `dispatch-owned WORKER`, then `claim-owned TASK_ID WORKER` for new engineering execution. Check the returned `claimed.id` before acting. Pass its `claim` object in the outcome JSON to `done-owned ID EVIDENCE OUTCOME` or `blocked-owned ID EVIDENCE OUTCOME`. These commands fence completion by ownership and require a real evidence file. Preserve foreign or legacy active tasks; they do not prevent claiming independent ready work. Do not infer ownership from the generic dispatch's next item. Checkpoint your current task before claiming another; card-stage claim tokens remain separately required.
- When dispatch has no eligible engineering task, run `node --experimental-strip-types scripts/engineering-work-queue.ts discover-pipeline` to admit up to ten fresh eligible card-stage tasks from the reviewed card queue, then claim again. Existing task IDs suppress unchanged retries. Execute each task through supported card commands; discovery/admission is not completion. Pricing and inventory work depend on a verified read-only seller session; recheck session access before use and isolate a shared access failure. Never treat an old access checkpoint as fresh four-scope inventory clearance.
- Resume blocked engineering work only with `resume TASK_ID EVIDENCE_FILE NEW_INPUT_VERSION`, describing the changed evidence and retaining the old blocker in history. User decisions are captured instructions, not fabricated credentials or proof of successful access.
- On actual seller-session failure, use `suspend-access seller-read-access EVIDENCE_FILE OUTCOME_FILE` (outcome includes `blocker`). This suspends the access dependency and interrupted engineering review while leaving independent local tasks eligible. Close/hold any owned card lease through its supported protocol. Resume access only after a fresh successful read, then explicitly recover interrupted card work.
- Before ending, check coverage for unfinished requests and record exact blockers/checkpoints. A queue entry or mock result is not implementation evidence. Update the overnight report and Legends OS 26 tracker with actual validation. Scheduled wakeups resume work; this CLI does not execute agents between runs.
