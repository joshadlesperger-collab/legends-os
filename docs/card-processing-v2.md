# Card Processing V2

## First-pass execution controls — November 3, 2026

Prepare correctly once, save once, compare actual saved values read-only, correct only demonstrated defects, and archive each independently verified card immediately. Preparation and saved readback share the same factual description contract. Acceptable existing wording and supported inert HTML formatting retain their original bytes and provenance; the literal word Base is optional. Unknown or active HTML remains an exception. Explicit holder-only optical caveats remain visible as photo notes; genuine identity uncertainty, damage, grading and pairing exceptions still hold. The validated original identification result is retained before normalization; settled calls are not repeated.

The internal-browser job CLI adds two supported operations:

- `audit` with `{id, observations:[{cardId,evidence:{path,sha256}}]}` evaluates fresh actual saved editor observations against frozen job payloads. It makes no editor writes. Passing rows require no correction; observed defects produce scoped correction targets. Missing, stale, foreign or ambiguous evidence remains held without speculative edits. Generic section labels do not prove blank policy values.
- `verify-ready` with `{id,lease,review:{evidence:{path,sha256}},archiveAuthority}` verifies and hash-archives an exact eligible subset through the existing strict review/archive protocol. Other cards stay untouched. The whole job remains incomplete until every selected card has verified saved fields and moved-photo receipts. Existing `finish` still requires complete job coverage.

Use batch readback only when it supplies equivalent actual per-card field and photo evidence. These operations consume retained observations; they do not add a native bulk capture adapter or an attached unattended browser executor. Fixture tests prove the local controls, not live throughput. Pricing stays with Grok and publication remains unavailable. See `AGENTS.md` and `docs/LISTING_WORKFLOW.md` for the standing procedure.

Card Processing V2 is a separate local workflow at `/card-processing-v2`. Its queue, flat verified-card repository, usage ledger and run checkpoints live under `artifacts/card-processing-v2`. It does not replace the Listing Factory or migrate unfinished inventory. Existing evidence is read for duplicate exclusion; existing inventory, drafts, source queues and prices remain owned by their current workflows.

## Process New Cards

Scan into the existing configured folder, open **Card Processing V2**, and click **Process New Cards**. This starts a real local worker process with a bounded batch; the dashboard refreshes its persisted checkpoints. The stage counts represent physical captures, while draft-group counts represent consolidated rows. An exception includes its owner and next action. A saved upload count, generated CSV or local prepared row is never shown as a verified eBay draft.

The default source folder is `CARD_SCANNER_PATH`, then `CARD_INBOX_PATH`, then `C:\CardScans` on Windows. The V2 configuration file is `artifacts/card-processing-v2/config.json`. `folder` selects the existing folder; `pairing` is `named` or explicitly configured `alternating`; `batchLimit` defaults to 10 and accepts 1–20. Keep the worker on the local host that owns the scan folder. Cloud deployments cannot access that folder and do not launch this scanner worker.

Only new, unowned captures enter V2. Existing inventory and previously owned photos are excluded. An original capture is counted once; a copied file or retry cannot create another unit. Distinct original captures remain distinct physical cards even when their content is visually identical. Exact unnumbered identity, artwork, variant, language and condition can consolidate into one quantity group. Different serial-numbered copies stay separate. An additional capture arriving after a draft/submission intent requires reconciliation instead of silently changing a pending quantity.

## Identification and completeness

OpenAI performs identification only. Both frozen original sides, pairing and orientation must be supported; uncertainty, visible damage and graded cards become exceptions. No eBay photo AI substitutes for identification. Successful per-capture identification is checkpointed so restarts reuse it. The flat verified repository retains identity, original hashes, verification time and evidence, without introducing a graph database. Product-level information never proves the identity, condition or serial of another physical copy.

Identification calls require configured OpenAI access and a V2 identification configuration containing the selected `model`, captured spending `authority`, bound expiry, pricing-source URL, input/output rates, token/request limits and cumulative `capMicros`. Rates and billing bounds must be verified for the selected model; do not paste guessed prices into configuration. Reservations precede calls, and actual usage is retained afterward. A crash or unknown billing result remains uncertain and cannot trigger a blind repeated paid call. The dashboard's cost per identified physical card is attributable V2 identification cost; it does not imply all subscription, eBay or later pricing costs are known.

Before a draft payload can be created, formal completeness checks require:

- A searchable title retaining name, year, product, card number, variant and serial within 80 characters.
- A verified category requirements snapshot from the last seven days, required item specifics and supported category values. Category snapshots belong in `categories` in the local configuration; do not invent a required-aspect list to clear a hold.
- Exact upright front/back photo hashes with eBay-hosted HTTPS URLs valid for at least 24 hours.
- Supported Near mint or better condition encoding for the category. Graded or visibly damaged cards require separate supported review.
- A factual reviewed description. eBay AI descriptions may be used only where the actual draft editor supports them, after correct identity/title/specifics are present and after reviewing the generated text.

Grok pricing and shipping remain a separate handoff. An unpriced preparation record explicitly says `unpriced-grok-pending`; neither OpenAI nor the CSV exporter guesses a price or shipping charge. Actual Grok proposals retain the existing source-first evidence, pricing policy and required independent reviews. Listing preparation does not authorize publication, live repricing or changes to unfinished inventory.

## Supported draft lifecycle handoff

`lib/card-processing-v2-draft-lifecycle.ts` supplies the write-ahead and evidence protocol for a separately supported operator upload. It does not invent a Seller Hub draft API or perform an external upload. The protocol has three operations, and each operation holds the V2 worker lease while updating its local checkpoint:

1. **Begin:** `beginV2Draft(root, groupId, payload, reconciliation)` checks validated method evidence, the exact prepared group, current category completeness, cached media and every original's hash. Reconciliation must be a fresh seller-bound observation of drafts, active, sold and scheduled inventory, within 60 minutes, containing every capture ID and its original SKU. Any existing disposition holds the new creation and directs reconciliation to the existing ID. An immutable operation file and submission intent are committed before the function returns its submission key. Another begin cannot reupload the same group or overlapping captures.
2. **Import:** `recordV2Import(root, key, receipt)` binds the actual Draft import job, SKU and draft ID to that intent. The receipt includes a retained artifact path and SHA256. An actual import-row observation must match the successful result. Conflicting IDs or jobs become uncertain, preserving the existing mapping and prohibiting blind replacement. Same-ID reconciliation may recover the operation; an import response never marks the card verified.
3. **Verify:** `verifyV2Draft(root, key, readback)` compares the actual saved/reopened draft with every frozen payload field and exact expected policy/location bindings. The readback must identify the same seller, draft ID and eBay URL, contain no editor errors, and explicitly observe `savedItemPrice: null` for the unpriced route. `savedShippingAmount` records the actual amount or null separately from whether shipping is unresolved. Source bytes and capture identity are checked again before seeding the verified repository. Seller, identity, condition and ownership holds cannot be cleared by verification.

Every external observation packet contains `evidence: { path, sha256 }`; its artifact file is the exact structured observation without the `evidence` field. The artifact must remain inside `artifacts`, match its hash, and be at most 1 MB. The expected formats are exported as `v2DraftReconciliationSchema`, `v2ImportReceiptSchema`, `v2SavedDraftSchema` and `v2DraftPoliciesSchema`. They are designed for attributable observed evidence, not synthetic completion records.

The begin reconciliation packet contains `seller: "imaydit58"`, `source: "live-seller-read"`, `observedAt`, four true `scopes` flags, `captures`, and `expectedPolicies`. Each capture contains its `captureId`, original `sku`, disposition and existing item/draft `id` where applicable. Expected policies include exact `payment`, `returns: "No Return Accepted"`, `shipping` or null, `location`, and `pricingShippingUnresolved`; blank inherited policy fields cannot pass as complete.

The import evidence artifact contains `kind: "live-ebay-draft-import-row"`, `seller: "imaydit58"`, `action: "Draft"`, `jobId`, `draftId`, `sku`, `result: "Success"` and `observedAt`. The import packet contains the job ID, draft ID, observation time and evidence reference.

The saved-readback artifact contains `kind: "saved-reopened-ebay-draft"`, seller, draft ID, exact draft URL, observation time, actual full `payload`, actual `policies`, `savedItemPrice: null`, `savedShippingAmount`, and `editorErrors: []`. Its packet adds the evidence reference. A blank-item-price observation is mandatory; a fixed local pricing label alone is insufficient proof of eBay's saved field.

Successful verification marks the mapped captures verified and stores exact-photo verified knowledge. It explicitly retains **Archive pending** and the supported receipt/archive next action. This V2 lifecycle does not manufacture an old orchestrator `QueueState`, move originals directly, or pretend that a pending archive is complete. `verified` describes the observed eBay draft milestone; final batch completion still requires the actual supported archive result. Run `node --experimental-strip-types --test tests/card-processing-v2-draft-lifecycle.test.ts` for this protocol's regression checks.

### Reviewed eBay AI descriptions on the same draft

After the imported draft has the correct title, category and item specifics, an available actual eBay editor capability may generate its description. Review that text against the frozen card evidence, removing unsupported claims and contradictions. Before saved-draft verification, record the actual generation and attributable review with `reviewV2DraftDescription(root, key, packet)`. This operation does not invoke an eBay API or imply the capability exists in an unavailable editor.

The `v2ReviewedDescriptionSchema` packet requires `kind: "reviewed-ebay-ai-description"`, seller, same draft ID and URL, actual `generatedAt` and review `observedAt`, `capability: "ebay-editor-description-ai"`, a named `reviewer`, `reviewed: true`, `unsupportedClaims: false`, `contradictions: false`, the current `beforePayloadHash`, exact existing `title`, `categoryId` and `specifics`, and the reviewed `description`. As with other observation packets, add a hash-bound artifact reference whose JSON is the packet without `evidence`. The observations must be fresh and after the original draft intent. The review flags are attributable review findings; the application does not pretend that a text regex independently proves every factual claim.

Only description text and `descriptionSource: "ebay-ai-reviewed"` can change. Price, condition, identity, category, title, specifics, quantity and photos stay bound to the original intent. Unsupported text, another draft, changed binding fields, extra pricing/identity fields, mismatched evidence bytes and seller/identity/condition/import holds are rejected. Descriptions use the shared payload limit; HTML and control/formula content remain excluded from this plain-text preparation contract.

Every accepted description review writes an immutable amendment containing the original begin reference, prior payload/capture hashes, prior checkpoint reference, next full expected payload/capture hashes and the actual observation. The submission key and draft ID remain stable. The original begin proof is never rewritten. Verification replays the whole description-only chain against that original proof and compares the actual saved/reopened full text with the latest reviewed version. A changed saved description without a bound review fails verification. Accepted reviews remain pending save/reopen; they do not verify, publish or archive the draft.

## Actual Seller Hub Feed uploader

The supported OAuth route for uploading Draft templates is the eBay Sell Feed API's **FX_LISTING** feed type, schema version **1.0**. eBay's [Seller Hub feed flow](https://developer.ebay.com/api-docs/sell/static/feed/fx-feeds-overview.html) explicitly directs production-only tests to the Draft action, and its [quick reference](https://developer.ebay.com/api-docs/sell/static/feed/fx-feeds-quick-reference.html) includes Create new drafts. This produces Seller Hub drafts rather than Inventory API offers. The adapter never calls offer, publish, Add, Revise, Relist or End operations.

`lib/card-processing-v2-uploader.ts` implements `createTask`, multipart `upload_file`, bounded same-task status polling and `download_result_file` against the fixed production Feed endpoint. It uses the existing supported seller OAuth connection; seller authorization for the Feed API and applicable inventory scope are required. A token alone does not prove account entitlement. An actual refused call retains a sanitized access/operation checkpoint; no draft completion is inferred.

`uploadV2DraftIntents` runs only after the local worker releases its lease. It accepts 1–20 already-created exact V2 intents, rechecks original bytes, current completeness, fresh four-scope clearance and all holds before each new mutation, and serializes a Draft-only CSV. It persists per-intent batch ownership, exact CSV hash, physical input-line mappings and request stages before network mutations. The actual Feed task ID is retained before any upload. Caller ordering, subset requests and overlapping captures cannot create another batch.

An uncertain task-creation response cannot automatically create another task. An uncertain upload with a known task ID resumes with GET requests only. Processing remains bounded; a later invocation resumes the same task. Downloaded result bytes are retained and hashed. Each result must map to its exact input line and SKU where supplied; the real retained eBay report sometimes leaves CustomLabel blank, so counts or guessed SKU order are insufficient. Duplicate or unknown result rows, active ItemIDs and conflicting draft IDs stop reconciliation. Successful rows receive their actual same draft ID; failed and missing rows retain independent exceptions and are never automatically reuploaded.

The uploader always reports `verified: false`. A successful Feed import is the **submitted** milestone. Actual saved/reopened editor values, supported condition/policy completion, any available reviewed eBay AI description and the verified archive handoff remain separate mandatory steps. No public full-detail Seller Hub draft getter or unattended editor capability is invented here. A Codex computer-use session is not an app-runtime browser transport.

An explicitly captured, exact new-capture pilot can bootstrap method validation without claiming the method is already proven. The optional fifth `beginV2Draft` argument is `{ pilot: { instructionId, captureIds, expiresAt } }`; its captured instruction must reference `card-processing-v2-draft-pilot` and the linked V2 live-validation task. Capture scope must exactly match, expire within an hour, and exclude activation originals/unfinished inventory. The immutable begin proof records `pilot-unvalidated`; actual observed repairs and elapsed time must be reported. This does not rewrite the older separate zero-repair/throughput experiment or its failed result.

Run `node --experimental-strip-types --test tests/card-processing-v2-uploader.test.ts` for transport and restart regressions. The retained official API contract is `artifacts/card-processing-v2-implementation/fx-listing-official-contract-20261103.json`; it is documentation evidence, explicitly not a live upload receipt.
